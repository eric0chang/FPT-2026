# Topic 6: Streams and FIFOs (12 rules)

Covers: hls::stream, FIFO depth, blocking/non-blocking access, deadlock. `must` / `must-not` first. Full rule: `../HLS/<ID>.md`.

| ID | Type | Summary | Tags |
|---|---|---|---|
| HLS-1302 | must | Use hls::stream only in C++ designs, always pass it to functions as a reference (hls::stream<T>&), and ensure each stream object has exactly one process writing it and one process reading it. | dataflow, pass-by-reference, stream |
| HLS-1022 | must-not | Do not rely on source order between accesses to different hls::streams: the scheduler may move a write to one stream before or after a read from another. Only accesses to the same stream are kept sequential. | hls-stream, ordering, scheduling |
| HLS-1303 | must-not | Do not use a class or struct with member functions as the element type of an hls::stream or split/merge channel; use C++ native types, arbitrary-precision types (ap_int, ap_ufixed, ...) or plain structs built from them. | data-type, split-merge, stream, struct |
| HLS-1306 | must-not | Do not use write_nb() on a stream mapped to an AXI4-Stream (axis) interface; axis supports only non-blocking reads, ap_fifo supports both. Top-level streams default to axis in the Vitis kernel flow and ap_fifo in the Vivado IP flow. | ap_fifo, axis, interface, stream, write_nb |
| HLS-1210 | pitfall | When a dataflow design deadlocks or underperforms in RTL co-simulation, inspect the Dataflow Viewer: it highlights the deadlocked processes/channels (e.g. FIFO too shallow) and gives per-process read-blocked/write-blocked stall percentages. | cosim, dataflow, deadlock, fifo-depth |
| HLS-1214 | pitfall | C sim treats streams as unbounded, so a too-shallow FIFO (hls::stream default depth 2, or a dataflow channel) shows only as a cosim/hardware stall or deadlock: outside DATAFLOW a stream must hold all producer output (XFORM 203-733); set STREAM depth from rates, or start at the item count and shrink. | cosim, dataflow, deadlock, fifo-depth, hls-stream |
| HLS-1304 | pitfall | Do not end a read loop on stream.empty() (while(!s.empty()) s.read();): C sim always has data so it completes, but one bubble in hardware exits early, so RTL differs from C sim. End the loop on the AXI4-Stream TLAST side-channel instead. | blocking, determinism, stream, tlast |
| HLS-1308 | pitfall | Since 2022.2, reading an empty hls::stream in C sim is an error (a deadlock error when hls::task is used), and unread leftover data gives a warning; both signal possible RTL sim hangs. Debug the blocked read; add -DHLS_STREAM_READ_EMPTY_RETURNS_GARBAGE only if empty reads are intended. | csim, deadlock, hls-task, stream |
| HLS-1005 | direction | Prefer sequential data access patterns in HLS code: in software random access is almost free, but in hardware sequential access is what pays off, because it can be converted into a stream between tasks. | access-pattern, sequential-access, streaming |
| HLS-1006 | direction | Choose dataflow channel types by trade-off: PIPO (ping-pong) channels overlap tasks with no deadlock risk because the tool matches production and consumption rates; FIFOs let consumers start sooner, element by element, but can deadlock unless sized correctly. | dataflow, deadlock, fifo, fifo-depth, pipo |
| HLS-1084 | direction | For data streamed into or out of the top function, prefer hls::stream over multi-access pointers; the manual strongly recommends it because a stream type models streaming hardware accurately and avoids the volatile-pointer simulation issues. | hls-stream, multi-access, pointer, streaming |
| HLS-1305 | direction | Prefer blocking stream access unless non-blocking is needed: blocking is deterministic but can deadlock on undersized FIFOs or unequal rates; read_nb/write_nb or empty()/full() guards may be non-deterministic, not fully checkable in C sim/co-sim (use an RTL test bench); ap_ctrl_none cosim may hang. | blocking, deadlock, determinism, hls-stream, non-blocking |
