# Topic 8: Verification (csim, cosim, testbench) (11 rules)

Covers: test benches, C simulation, C/RTL co-simulation. `must` / `must-not` first. Full rule: `../HLS/<ID>.md`.

| ID | Type | Summary | Tags |
|---|---|---|---|
| HLS-1191 | must | From the project's start, and after every source change, run a self-checking C test bench: drive the top function with stimuli, compare its outputs with golden reference data, and return 0 from main() only on a match; C sim and C/RTL co-sim judge pass/fail solely from that return value. | cosim, csim, golden-vectors, testbench, verification |
| HLS-1193 | must | For C/RTL co-simulation to yield performance data, the test bench must call the top function repeatedly: II is only measured over repeated calls, and Dataflow Viewer profiling needs at least two calls plus cosim.enable_dataflow_profiling=true in the config. | cosim, dataflow, ii, profiling, testbench |
| HLS-1194 | must | Register every file the C test bench reads or needs to run (stimulus/golden data files, bench sources) as tb.file, since the tool reuses the bench for RTL verification; a single file holding both design and bench must be listed as both syn.file and tb.file. | config, cosim, syn-file, tb-file, testbench |
| HLS-1192 | must-not | The test bench must not wait for interactive user input during execution, because the HLS tool cannot talk to the running simulator; pass any run-time arguments when launching simulation (csim.argv) or read them from files. | argv, csim, testbench |
| HLS-1211 | must-not | Do not drive co-simulation with run-time random stimulus (std::random_device, or a seed taken from the clock); fix the seed, or generate the random vectors once, store them in a file and let the C test bench read that file. | cosim, random, testbench |
| HLS-1216 | must-not | For cosim, a top-level interface array (or array in an interface struct) may carry at most one of: equal-size vertical map, reshape, dim-1 partition; and never horizontal map, different-size vertical map, array-to-stream map, or conditional AXIS access with register slice. | array-map, array-partition, array-reshape, cosim, interface |
| HLS-1054 | pitfall | If C simulation runs out of memory or crashes with very large local arrays (worse with ap_int/ap_fixed types), the arrays sit on the stack: enlarge it via syn.csimflags, or heap-allocate them for simulation only under `#ifndef __SYNTHESIS__`. | ap_int, array, csim, stack, synthesis-macro |
| HLS-1217 | pitfall | Cosim latency/II are measured for your stimulus and can differ from the synthesis report, whose values are bounds from shortest/longest paths. Non-pipelined: II = latency + 1; pipelined: II = cycles between ap_ready pulses. | cosim, ii, latency, report |
| HLS-1219 | pitfall | Cosim can fail although C sim passes if code relies on undefined behavior: uninitialized reads (e.g. a loop-local expected to keep the last iteration's value) or out-of-bounds indexes (N accesses on an N-1 array); C sim sees random values, RTL sees X. Initialize, and size arrays for every access. | array, cosim, out-of-bounds, undefined-behavior, uninitialized |
| HLS-1220 | pitfall | When the design uses floating point, make the test bench accept results within a tolerance, not exact equality: the RTL of some float math differs from C, standard math functions are bit-approximate (typically 1-4 ULP off), and unsafe_math_optimizations/no_signed_zeros change rounding. | cosim, floating-point, testbench, tolerance, ulp |
| HLS-1003 | recipe | Iterate an HLS component as: C-simulation with a C++ test bench, Code Analyzer (performance, parallelism, legality), C-synthesis with v++, C/RTL co-simulation reusing the same test bench, then review synthesis and implementation timing reports; repeat until goals are met. | code-analyzer, cosim, csim, flow, testbench |
