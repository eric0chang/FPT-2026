# Topic 5: Dataflow and task-level parallelism (25 rules)

Covers: DATAFLOW, PIPO/FIFO channels, STABLE. `must` / `must-not` first. Full rule: `../HLS/<ID>.md`.

| ID | Type | Summary | Tags |
|---|---|---|---|
| HLS-1027 | must | In DATAFLOW, an array channel accessed in arbitrary order must stay a PIPO (default size twice the array); only arrays accessed strictly sequentially may become FIFOs, which save memory but can deadlock if mis-sized, whereas PIPOs never deadlock. | array, dataflow, deadlock, fifo, pipo |
| HLS-1185 | must | Every variable passed between DATAFLOW tasks must be written by exactly one task and read by exactly one (a split task can copy data for each extra consumer); for canonical form, also call the producer before the consumer for local channels and the reader before the writer for region arguments. | canonical-form, dataflow, fanout, single-producer-consumer |
| HLS-1311 | must | Place an hls::task or ap_ctrl_none region only in a parallel context (top, task-only function, ap_ctrl_none chain up to the top, or a dataflow region between processes feeding and draining it), never directly in sequential or pipelined code; same for control-driven dataflow in a pipeline or task. | ap_ctrl_none, dataflow, hls-task, pipeline, task-level-parallelism |
| HLS-1188 | must-not | Do not execute DATAFLOW tasks conditionally (e.g. if/else choosing which loop runs): dataflow does not optimize them. Make every task run on every call and move the condition inside the loop body. | conditional, dataflow, loop |
| HLS-1189 | must-not | Do not use loops with more than one exit condition in a DATAFLOW region: a loop containing break or continue cannot be a dataflow task; its only exit must be the loop bound. | break, continue, dataflow, loop |
| HLS-1237 | must-not | Do not put single-producer-consumer violations, feedback between tasks, conditionally executed tasks, or loops with multiple exit conditions in a DATAFLOW region: HLS then just issues a message and skips the DATAFLOW optimization. | dataflow, feedback, spsc, task-level-parallelism |
| HLS-1029 | pitfall | An array streamed as a FIFO in a DATAFLOW region can lose the strictly sequential accesses streaming relies on to compiler optimizations, dead code elimination especially; declaring it volatile may be needed to block them and keep streaming correct. | dataflow, fifo, stream-pragma, volatile |
| HLS-1030 | pitfall | If compiler-created DATAFLOW FIFOs limit throughput (or, for scalar ones, deadlock), resize them: start FIFOs (ap_start/ap_ready to internal processes) via syn.dataflow.start_fifo_depth, scalar FIFOs via syn.dataflow.scalar_fifo_depth; or drop start FIFOs (disable_start_propagation) at own risk. | dataflow, disable_start_propagation, fifo-depth, start-fifo |
| HLS-1184 | pitfall | In a DATAFLOW region, read the function's input ports at the start and write its output ports at the end; port accesses in the middle of the region can make the processes execute one after another instead of overlapping. | dataflow, interface, overlap |
| HLS-1186 | pitfall | When a DATAFLOW PIPO channel bypasses tasks (written by one task, first read two or more tasks later) and throughput drops, raise its depth from the default 2 to 3 if it skips one task or 4 if it skips two, via STREAM type=pipo depth=N; each extra unit costs one more array buffer. | backpressure, bypass, dataflow, fifo-depth, pipo |
| HLS-1012 | recipe | To make code blocks such as loops run concurrently in hardware, place each block in its own function: as a general rule the HLS compiler infers task-level parallelism only from function calls. | dataflow, function, loop, task-level-parallelism |
| HLS-1014 | recipe | To overlap successive invocations of a task chain (task-level pipelining), use double buffering / PIPO channels between tasks, so a producer's next run cannot overwrite data its consumer is still reading. | dataflow, double-buffer, pipo, task-pipelining |
| HLS-1025 | recipe | For a predictable function-level DATAFLOW region, make the body only local non-static scalar/array declarations plus a sequence of non-inlined void calls, with no if, loop, return, goto or throw between them; put control inside the called processes. | canonical-form, control-flow, dataflow, strict-mode |
| HLS-1026 | recipe | For DATAFLOW inside a loop, the enclosing function should hold only the for loop, whose variable is declared in the header starting at 0, bounded by a non-negative constant or scalar argument, stepped by 1, with the DATAFLOW pragma inside the loop body. | canonical-form, dataflow, loop |
| HLS-1028 | recipe | To make an array written or read strictly in order a FIFO instead of a RAM or DATAFLOW ping-pong (PIPO) channel, apply `#pragma HLS stream variable=<arr>`, preferably over global syn.dataflow settings; the FIFO defaults to the array's size, but depth=N can be far smaller (even 1 at II=1). | array, dataflow, fifo, fifo-depth, stream-pragma |
| HLS-1187 | recipe | Avoid feedback (a later DATAFLOW task feeding an earlier one): HLS may warn and skip dataflow. If needed, carry it only over hls::stream or hls::stream_of_blocks (arrays/PIPOs flow forward only; plain variables must not carry it), and handle the first call, when the channel is still empty. | dataflow, feedback, hls-stream, loop-carried, stream-of-blocks |
| HLS-1218 | recipe | To locate dataflow bottlenecks after cosim, set cosim.trace_level=all and cosim.enable_dataflow_profiling=true; the Timeline Trace shows each process's start/end and FIFO/PIPO full/empty stall shares. Optimize the processes dominating runtime. | cosim, dataflow, fifo, pipo, profiling |
| HLS-1263 | recipe | Mark a DATAFLOW region argument with `#pragma HLS stable variable=<v>` if, while the region runs, nothing overwrites what it reads or reads what it writes first (e.g. config ports changed only while idle): its task-level sync is dropped, so iterations overlap and II improves. Control-driven only. | control-driven, dataflow, ii, stable, synchronization |
| HLS-1004 | direction | Decompose a sequential algorithm into small producer and consumer tasks linked by streams, so a consumer can work on each item as soon as it is produced instead of waiting for the whole batch; on FPGA these tasks then run concurrently. | dataflow, decomposition, producer-consumer, streaming, task-level-parallelism |
| HLS-1009 | direction | In a producer-consumer (dataflow) design, pipeline the inside of every task and size its streams so each task produces and consumes data at a high rate; interruptions in the data fed through the network lower its performance. | dataflow, fifo-depth, pipeline, streaming, throughput |
| HLS-1013 | direction | Tasks that exchange no data, share no memory and need no shared compute resource can run in parallel (fork-join within one run), like B and C in a diamond A -> (B, C) -> D where A writes a separate array for each. | dataflow, fork-join, shared-memory, task-level-parallelism |
| HLS-1016 | direction | Avoid communication channels with very wide bit-widths; splitting such a channel into several narrower ones eases implementation on the FPGA. | bit-width, channel, streaming |
| HLS-1024 | direction | Apply DATAFLOW to a function or loop body to let its sequential sub-functions overlap (start before the predecessor ends, restart early, run concurrently) while keeping C++ semantics; expect extra FIFO/ping-pong resources and confirm the overlap in co-simulation. | cosim, dataflow, fifo, pipo, throughput |
| HLS-1235 | direction | For a dataflow PIPO, binding a single-port RAM typically gives a merged PIPO (one memory, producer and consumer on different halves), cheaper for small PIPOs; a dual-port binding whose two ports get used typically yields a split PIPO, one memory per block. | bind_storage, dataflow, pipo, ram_1p |
| HLS-1264 | direction | Choose STREAM type= by sync need: pipo keeps duplicate buffers (depth banks, default 2); shared syncs like PIPO without copying data (default depth 1); unsync syncs only individual accesses, so your design must guarantee access order. | channel, dataflow, pipo, stream |
