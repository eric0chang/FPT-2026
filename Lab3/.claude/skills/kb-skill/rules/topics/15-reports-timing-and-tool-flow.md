# Topic 15: Reports, timing and tool flow (17 rules)

Covers: reading synthesis reports, clock/timing, tool settings, runtime, general design flow. `must` / `must-not` first. Full rule: `../HLS/<ID>.md`.

| ID | Type | Summary | Tags |
|---|---|---|---|
| HLS-1204 | must-not | Do not hand RTL from the syn/ or impl/ verilog or vhdl folders straight to Vivado; use the packaged IP export (impl/ip): designs using Vivado catalog IP (e.g. floating point) need IP-creation scripts that only the package flow runs, so those folders can be an incomplete design. | floating-point, ip, packaging, rtl, vivado |
| HLS-1001 | pitfall | After upgrading to 2023.2, II and latency of designs that passed before can change: the scheduler's delay model is more pessimistic (closer to Vivado), notably for AXIS interfaces and complex pipeline-control enables. If timing was met before, pin II/latency with pragmas. | axis, ii, latency, migration, timing-model |
| HLS-1208 | pitfall | Pragmas can end up ignored or not applied as intended; after each synthesis run check the Pragma Report in the Synthesis Summary, which lists valid, ignored and inferred pragmas with links to their source lines. | ignored, pragma, report |
| HLS-1015 | recipe | Before coding or refactoring, settle the macro-architecture (model it as producer-consumer tasks) and draw an expected activity timeline of when each function runs across several invocations; later compare it with the parallelism actually achieved. | architecture, planning, producer-consumer, timeline |
| HLS-1197 | recipe | To act on Code Analyzer findings, rewrite the source in dataflow form yourself: outline each process into its own function and add a DATAFLOW pragma to the function, loop or region; merges/splits done in the report never change your code. | code-analyzer, dataflow, refactor |
| HLS-1198 | recipe | Before synthesizing a dataflow design, scan the Code Analyzer channel table for canonical-form violations: R+W on channels from Start/to End, one variable carried by several channels, and channels with mode R→W or R+W→W (feedback). | canonical-form, code-analyzer, dataflow, legality |
| HLS-1199 | recipe | To speed up a dataflow region without synthesis, target the process with the largest TI (red in Code Analyzer's TI heat map) and its Performance Guidance issues; reaching II=1 on an inner loop requires fixing every issue listed for that loop nest. | code-analyzer, dataflow, ii, ti |
| HLS-1203 | recipe | When a loop must be unrolled (explicitly, or automatically by a PIPELINE higher in the hierarchy), move its body into a separate function to cut synthesis runtime; pipeline that function if the unrolled loop sits in a pipelined region. | function, pipeline, runtime, unroll |
| HLS-1206 | recipe | Reading Performance Estimates: latency counts cycles until the last output (last element of an array output); a function or loop without PIPELINE runs iterations back to back and has II = latency + 1; Trip Count shows hardware iterations after unrolling; the Slack column flags timing issues. | ii, latency, pipeline, report |
| HLS-1221 | recipe | When Vivado implementation misses timing, trace the worst-slack paths (top 10 by default) back to C via the report's Resources table and break long combinational paths; if logic levels and fanout jump from RTL synthesis to P&R, suspect congestion and rewrite C or change BRAM/LUTRAM/URAM choices. | congestion, critical-path, fanout, implementation, timing |
| HLS-1254 | recipe | To make several port writes (e.g., a data value and its valid flag) change in the same clock cycle, enclose them in a { } region with #pragma HLS LATENCY min=0 max=0. | io-timing, latency, region |
| HLS-1261 | recipe | To keep an exact cycle-by-cycle I/O sequence (e.g., a handshake), put the code in a named { } region with #pragma HLS protocol; HLS inserts no clock cycles there, so add ap_wait() where a cycle boundary is needed. | ap-wait, io-timing, protocol |
| HLS-1158 | direction | The clock period drives scheduling: a longer period lets more chained operations complete within one cycle, while a shorter one makes HLS spread operations over more cycles or use multi-cycle units automatically. | chaining, clock, latency, scheduling |
| HLS-1196 | direction | Turn on Code Analyzer (csim.code_analyzer) with C simulation to get a pre-synthesis dataflow graph, transaction-interval (TI) and throughput estimates, and blocker hints; it is quick but less accurate than synthesis, so confirm its conclusions by synthesizing. | code-analyzer, csim, dataflow, ti |
| HLS-1201 | direction | clock and clock_uncertainty can change synthesis results: they affect timing and operation scheduling, and the uncertainty share of each cycle is held back for the Vivado back-end (place and route) rather than used by HLS operations. | clock, clock-uncertainty, scheduling, timing |
| HLS-1202 | direction | Apply loop unrolling, array partitioning and function inlining selectively, not everywhere: each adds objects the scheduler must handle and increases synthesis runtime, although they may be needed to meet performance. | array-partition, inline, runtime, unroll |
| HLS-1205 | direction | Treat C-synthesis II, latency, timing and resource numbers as estimates: use C/RTL co-simulation for measured II, latency and stalls (shown per module in the Function Call Graph), and Vivado synthesis or implementation for better timing/resources, which still shift in the full system. | cosim, estimate, function-call-graph, timing, vivado |
