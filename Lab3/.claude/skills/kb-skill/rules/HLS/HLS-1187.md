- Feedback between tasks is not recommended; depending on the situation the compiler warns and might not use the dataflow model. Stream channels are the stated exception: each stream still has one writer and one reader, so single-producer-consumer holds, and both tasks can keep running indefinitely.
- Loop-carried data across iterations also needs FIFO channels: arrays turned into streams allow forward dependencies only, hls::stream allows forward and backward. Exception: a dependency across successive calls of the top function (an inout argument written in one call and read in the next) is fine.
- DATAFLOW handles any DAG of processes; a cyclic network needs stream channels.
- hls::stream: streams have no initial value, so let the earlier task use a constant on its first call (static flag) and read the stream after that:
```cpp
void stageA(hls::stream<int> &fwd, hls::stream<int> &back) {
  static bool started = false;
  int v = started ? back.read() : 7;  // seed on first call
  started = true;
  fwd.write(v * 3);
}
void stageB(hls::stream<int> &fwd, hls::stream<int> &back) {
  back.write(fwd.read() - 1);
}
// top: #pragma HLS DATAFLOW; stageA(f, b); stageB(f, b);
```
- hls::stream_of_blocks (block-sized feedback in a dataflow loop): on the first iteration nothing has been produced yet, so the consumer checks `empty()` and returns. Give the channel ample depth: under `ap_ctrl_chain` the producer must finish before the consumer runs again (the manual's example uses M+2); a smaller depth would need `ap_ctrl_none`.
Also covered in UG1399 Ch.2 Abstract Parallel Programming Model for HLS > Canonical Body, pp. 50-51.
Also covered in UG1399 Ch.27 HLS Stream of Blocks Library > Modeling Feedback in Dataflow Regions, pp. 769-770.
