- Vitis HLS maximizes performance first by default, so it will not minimize operator count unless told to.
- Scheduling decides which operators run in each cycle and how many are needed; binding then assigns each operation to a hardware instance, so only operations scheduled in different cycles can share one unit. An ALLOCATION limit makes HLS reuse units across cycles, which may lengthen the schedule.
- Two kinds: `function` (named functions; e.g. four calls to one helper collapse into a single RTL block with `#pragma HLS allocation function instances=helper limit=1`) and `operation` (adds, multiplies, array reads/writes; full list under config_op).
- Typical use: a fully unrolled loop needs 317 multiplies but the device has only 256 DSPs.
- A limit higher than required gives less sharing: HLS uses either the limit or the maximum it needs.
- Without directives, HLS picks each operator's implementation (e.g. combinational vs pipelined multiplier) from the clock constraint and device delays; the type option can cap an implementation (e.g. combinational multipliers, pushing the rest onto pipelined ones).
- Controllable operators are listed in Table 21 (add, sub, mul, sdiv/udiv, srem/urem, shl/lshr/ashr, icmp, f*/d* float ops); BIND_OP accepts only a subset.
```cpp
int dot(int a[317], int b[317]) {
#pragma HLS ALLOCATION operation instances=mul limit=256
  int s = 0;
  for (int n = 0; n < 317; n++) {
#pragma HLS UNROLL
    s += a[n] * b[n];
  }
  return s;
}
```
