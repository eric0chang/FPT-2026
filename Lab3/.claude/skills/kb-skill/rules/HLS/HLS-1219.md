id: HLS-1219
summary: Cosim can fail although C sim passes if code relies on undefined behavior: uninitialized reads (e.g. a loop-local expected to keep the last iteration's value) or out-of-bounds indexes (N accesses on an N-1 array); C sim sees random values, RTL sees X. Initialize, and size arrays for every access.

- Loop bounds that overrun the array size are a frequent cause.
- Loop-locals: on a CPU the variable tends to stay in the same register or stack slot, so it seems to persist across iterations; HLS gives no such guarantee and may not even perform code that follows the undefined read. Scalars produced by complete array partitioning behave the same way. Initialize the variable in every iteration if a fresh value is meant, or move its declaration above the loop (as high as needed) so its lifetime matches the intended reuse.
- Confirm the C simulation output is as expected and that no output got a random value.
- Valgrind, run outside the HLS environment, can confirm the C code is free of undefined or out-of-bounds accesses.
Also covered in UG1399 Ch.7 Unsupported C/C++ Constructs > Undefined Behaviors, p. 148.

Source: UG1399 v2023.2, Ch.12 Building and Running an HLS Component > Troubleshooting C/RTL Co-Simulation, p. 391.
